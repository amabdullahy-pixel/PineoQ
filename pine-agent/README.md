# README.md — Pine Agent

A modular agent architecture for **Pine Script v6** engineering on TradingView.
Requests are processed through a gated pipeline; every stage produces a
machine-checkable YAML contract, and no stage can be skipped.

## Pipeline

```text
Request
→ Routing
→ Formalization
→ Pre-Verification
→ Feasibility
→ Implementation Planning
→ Implementation
→ Post-Verification
   ↳ (incident path) Incident Intake — Phase 11: report + screenshot → structured incident contract → DATA_ACQUISITION_AND_ALIGNMENT
        ↳ Data Acquisition & Alignment — Phase 12: market data + provenance → aligned dataset → data contract → EXECUTION_TRACE_AND_DEBUG (open only for READY/READY_WITH_WARNINGS)
             ↳ Execution Trace & Debug — Phase 13: fingerprint-verified dataset + Pine-subset reconstruction → execution trace contract → ROOT_CAUSE_ANALYSIS (open only for READY/READY_WITH_WARNINGS)
```

| Stage | Purpose | Responsibility | Contract / config | Gate |
|---|---|---|---|---|
| **Request** | Capture the raw user request verbatim | Entry point; nothing is inferred yet | recorded in formalization input | — |
| **Routing** | Classify task, pick minimum Skills | Read request → classify → extract triggers → search `skills/registry.yaml` → select minimum Skills + mandatory dependencies → exclude the rest → report selection | `meta/skill_router.md`, `config/routing.yaml`, `skills/registry.yaml` | Stops (controlled failure) if registry empty or no trigger matches |
| **Formalization** | Convert language into precise spec | Normalize request; extract variables, formulas, boolean conditions; record assumptions, **ambiguities** (never silently resolved), edge cases, timeframes, MTF flag, repaint risk | `formalization/contract_schema.yaml` (v1.1), `meta/formalization_procedure.md`, engine: `formalization/formalize.pl` | Accepts only a `ready` routing/2 handoff; `implementation_allowed` becomes `true` only when every behavior-affecting ambiguity is `resolved_by_user` |
| **Pre-Verification** | Verify intent before any code exists | Logic, math, variable definitions, required data, assumptions, ambiguities, edge cases, feasibility prerequisite, MTF, repaint risk | `verification/pre_contract_schema.yaml` (v1.1), `meta/pre_verification_procedure.md`, engine: `verification/pre_verify.pl` | Accepts only an approved formalization contract (`--gate-check`); any blocker halts pipeline |
| **Feasibility** | Decide whether the request CAN be built | Evidence-bounded decision layer: capability scan (knowledge base seeded only from Import-Mode evidence), runtime model, timeframe/MTF, data availability, repaint risk mirrored verbatim, drawing/alert/session/performance advisory unknowns, per-requirement classification (EXACT/PARTIAL/NOT_FEASIBLE/UNKNOWN_REQUIRES_VERIFICATION) | `feasibility/contract_schema.yaml` (v1.1), `meta/feasibility_procedure.md`, engine: `feasibility/feasibility.pl`, `config/feasibility.yaml` | Accepts only an approved pre-verification result (`--gate-check --feasibility`); any blocker halts; unavailable items recorded, never substituted |
| **Implementation Planning** | Blueprint the code without writing it | Modules, data flow, state, MTF, signal, drawing, alert, performance architecture; 14 mechanical checks IP01–IP14; deterministic dependency graph + topological order; no semantic drift; no-Pine invariant | `implementation/contract_schema.yaml` (v1.1), `meta/implementation_planning_procedure.md`, engine: `implementation/implementation_plan.pl` | Accepts only an approved feasibility result (`--gate-check`); only FEASIBLE / FEASIBLE_WITH_WARNINGS open; PARTIALLY_FEASIBLE / NOT_FEASIBLE / BLOCKED / INVALID_INPUT never reinterpreted |
| **Implementation** | Produce Pine v6 code from the approved plan | Write code strictly per plan and contracts | `implementation/contract_schema.yaml` (output fields) | Forbidden until all upstream gates pass |
| **Post-Verification** | Verify the artifact after Implementation | Syntax, types, scope, runtime behavior, signal equivalence, repainting, MTF, performance, edge cases, alerts | `verification/post_contract_schema.yaml`, `config/verification.yaml` | Failures roll back to Implementation |

Ordering is enforced, not advisory: **Formalization always precedes code
generation; Feasibility sits between Formalization and Implementation; the two
verification stages never merge.**

## Implemented engines

Five stages are executable today (core Perl 5, zero non-core dependencies;
run with the stock Git-for-Windows Perl):

- **Router** — `perl skills/agent/router.pl --request "TEXT"` emits the
  routing/2 contract (YAML; `--json` and a v0.1 adapter also available).
  Acceptance: `--selftest` (80/80, TEST-ROUTING-001..008) and
  `--scenarios tests/routing/scenarios/scenarios.yaml` (57/57).
- **Formalization** — `perl formalization/formalize.pl --request-text "TEXT"
  --routing ROUTING_YAML` converts a `ready` handoff into the formalization
  contract (v1.1). `--resolve ID=resolved_by_user` records user decisions
  (`resolved_assumed` never unlocks the gate); `--gate-check --contract FILE`
  is the executable ordering gate for the next stage. Acceptance:
  `--selftest` (106/106, TEST-FORMAL-001..013).
- **Pre-Verification** — `perl verification/pre_verify.pl --contract
  FORMALIZATION_YAML` executes the 14 mechanical checks (PC01–PC14) against
  the formalization contract and emits the pre-verification result (v1.1)
  with a deterministic `verification_id`. `--gate-check --contract FILE` is
  the executable ordering gate for FEASIBILITY. Acceptance: `--selftest`
  (36/36, TEST-PRE-001..020).
- **Feasibility** — `perl feasibility/feasibility.pl --contract
  FORMALIZATION_YAML --pre PRE_RESULT_YAML` executes the 12 mechanical
  checks (FB01–FB12) against both upstream contracts and emits the
  feasibility result (v1.1) with a deterministic `feasibility_id`.
  Only FEASIBLE / FEASIBLE_WITH_WARNINGS set
  `implementation_planning_allowed: true`; unavailable capabilities/data
  are recorded in `unsupported_items`, never substituted; unknown platform
  limits stay `UNKNOWN_REQUIRES_VERIFICATION` (load-bearing unknowns block,
  prose unknowns warn). `--gate-check --feasibility FILE` is the executable
  ordering gate for IMPLEMENTATION_PLANNING. Acceptance: `--selftest`
  (55/55, TEST-FEAS-001..022).
  - **Implementation Planning** — `perl implementation/implementation_plan.pl --contract FORMALIZATION_YAML --pre PRE_RESULT_YAML --feasibility FEASIBILITY_YAML` executes the 14 mechanical checks (IP01–IP14) against all three upstream contracts and emits the implementation planning contract (v1.1) with a deterministic `planning_id`. The hard input gate rejects PARTIALLY_FEASIBLE / NOT_FEASIBLE / BLOCKED / INVALID_INPUT feasibility results — they are never reinterpreted as feasible; only FEASIBLE / FEASIBLE_WITH_WARNINGS set `implementation_allowed: true` and `next_stage: IMPLEMENTATION`. Modules are derived mechanically (M-DATA / M-CALC / M-STATE / M-SIGNAL / M-DRAW / M-ALERT / M-INTEG), the dependency graph is checked for cycles and missing deps, and the implementation order is the deterministic topological (Kahn) order. Behavior-bearing content is mirrored verbatim (no semantic drift); unresolved choices become `decisions[]` (NEEDS_USER_INPUT).`--gate-check --plan FILE` is the executable ordering gate for IMPLEMENTATION. Acceptance: `--selftest` (46/46, TEST-PLAN-001..027).
- **Implementation** — `perl implementation/implement.pl --plan PLAN_YAML --out RESULT_YAML --pine OUT.pine` consumes the authoritative Phase-8 plan verbatim and executes the Stage 02–10 gates mechanically: input/gate validation (S02), plan validation incl. dependency-cycle DFS and implementation-order coherence (S03), code architecture realization + module implementation strictly in plan order with zero invented behavior (S04/S05), integration (S06), compile validation reported honestly as `UNKNOWN_REQUIRES_EXTERNAL_VALIDATION` (S07 — no TradingView compiler exists locally; AGENT_RULES #21), static checks (S08, incl. the Pine v6 bool/na defect-class detector), traceability (S09), and determinism (S10) with a content-addressed `implementation_id` over identity chain + source sha256 + implementation order. The result contract (v1.1) carries no Pine source. Exit 0 only on `COMPLETED`. Acceptance: `--selftest` (10/10, TEST-IMPL-001..008).

## Operating principles

1. **Contracts between stages.** Handoffs are YAML documents inspectable by
   humans and machines; `status`, `blockers`, and `ambiguities` are first-class.
2. **Minimum-required Skill loading.** The Router never loads the full catalog;
   only trigger-matched Skills plus mandatory dependencies enter context.
3. **Honest verification.** Results are labeled ACTUALLY VERIFIED vs
   STATICALLY REVIEWED; no compiler exists in this environment, so compile
   confirmations must come from the user's TradingView run.
4. **Fail loudly, record everything.** Ambiguities and blockers stop the
   pipeline and are written down; nothing is guessed around.

See `AGENT_RULES.md` for the full binding rule set and
`meta/context_loading_policy.md` for context/token policy.
